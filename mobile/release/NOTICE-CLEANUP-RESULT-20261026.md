# إزالة ارتباط الإشعارات — خطوة مصدرية محددة

أضيف private.kinto_privacy_notice_cleanup_v1 فقط. لا تعديل لدوال الإرسال/القراءة المنشورة ولا للطلبات أو الدفع أو القارئات. الدالة غير مكشوفة للزائر أو المستخدم أو service_role، ولا يستدعيها مسار الإنتاج أو منفذ حذف الحساب الحالي.

تشترط طلب حذف موثق، تطابق العميل حرفياً، سياسة حذف مفعلة وبصمة مخطط مطابقة، وبنية مستلمين محددة دون محفز مستخدم أو علاقة واردة. تحذف ارتباط المستلم المحدد وread_at المرتبط به فقط؛ لا تحذف الإشعار أو الوسائط المشتركة. ناتجها يعلن account_deleted=false دائماً.

نجح الاختبار الفعلي في PostgreSQL مضمّن PGlite0.3.14 ببيانات مصطنعة: تعطيل السياسة، اختلاف هوية التأكيد، تغير المخطط، رجوع المعاملة، حفظ ارتباط العميل الآخر والإشعار المشترك وصف الطلب المدفوع، إعادة الاستدعاء دون ازدواج، غياب صلاحية anon، وإزالة المساعد بملف الرجوع. لا اتصال Supabase أو ملفات أو بريد أو طلب حقيقي.

إعادة التشغيل: تثبيت @electric-sql/pglite@0.3.14 خارج المستودع ثم NODE_PATH=<dependency-directory>/node_modules node mobile/privacy/notice-cleanup-check.mjs من جذر المشروع.

## الحد المتبقي

قفل جدول المستلمين يفرغ العمليات المتزامنة أثناء المعاملة، لكنه لا يمنع إضافة ارتباط جديد بعد COMMIT؛ دالة الإرسال الحالية لا تنسق نهائياً مع سجل حذف الحساب. لذلك لا ربط بالمُنهي أو تجاوز لحارس الجرد حتى تأهيل الكتابة المتأخرة. لم ينفذ اختبار جلستين حقيقيتين بهذه البيئة المضمّنة، ولا تمثل النتيجة تأهيل PostgreSQL17/Supabase الكامل. الرجوع يزيل الدالة فقط؛ لا يعيد ارتباطات محذوفة، لذا ليس تصريح تنفيذ.

ما زال حذف الحساب ذي المعاملات والملفات والنسخ غير مغلق. لا جاهزية رفع ولا دمج أو نشر.

## حارس إدخال الارتباط — مصدر تجريبي منفصل

أضيف حارس BEFORE INSERT/UPDATE OF customer_id يثبت صف العميل FOR KEY SHARE ويرفض الارتباط إذا لم يعد العميل موجوداً. لا يغير دوال الإرسال، ولا يعمل عند تحديث read_at وحده. اختُبر الإدخال لعميل موجود، وتحديث القراءة، ورفض إدخال/نقل ارتباط لعميل حُذف، وحفظ المستلم الآخر، وإزالة الحارس بالرجوع في PostgreSQL المضمّن.

لا نشر: لم يختبر سباق جلستين أو أثر مهلة القفل على إرسال جماعي؛ لا دليل على إغلاق ذلك. حارس الجرد العام ودالة التنظيف يرفضان المحفز الجديد عمداً حتى تأهيل بصمته وترتيب الأقفال مع المنفّذ الكامل. الملفان ليسا حزمة تثبيت متكاملة ولا تعليمات للمالك. لا يغير هذا account_deletion_fulfillment_tested=false.

## اختبار التزامن الجاهز للتشغيل

أضيف notice-owner-concurrency-check.py إلى فحص GitHub Actions المعزول. يختبر معاملتي إرسال/حذف متنافستين، ثم إدخالاً متأخراً بعد الحذف، مع مقارنة الطلبات قبل/بعد وحفظ إشعار مشترك ومستلمه الآخر. يرفض التشغيل دون KINTO_DISPOSABLE_TEST=1 وقاعدة kinto_privacy_test على127.0.0.1.

نجح فحص بناء Python ورفض البيئة غير المخصصة. لم ينفذ اختبار PostgreSQL ذي الجلستين هنا: تثبيت حزمة PostgreSQL17.10 نجح خارج المستودع، لكن النظام رفض تغيير مالك مجلد الاختبار وتشغيل الخادم كمستخدم غير root. لا نجاح CI مسجل لهذه الإضافة بعد ولا رفع للفرع في هذه الخطوة.

وجدت المراجعة أيضاً أن قفل جدول المستلمين ACCESS EXCLUSIVE في المساعد السابق لا يصلح دمجه تلقائياً مع حارس صف العميل: يمكن أن يعكس ترتيب أقفال الكاتب والمنهي. اختبار التزامن الجديد يستخدم أقفال الصفوف فقط؛ لا يستدعي المساعد السابق ولا يزعم تأهيله. يبقى المساعد منفصلاً ومقفلاً، ويلزم تعديله وتأهيله قبل أي تجميع إنتاجي.

## تصحيح ترتيب الأقفال — قيد التأهيل في CI

أزيل قفل جدول المستلمين الحصري من المساعد. يثبت المساعد صف العميل FOR UPDATE أولاً، ويتحقق من وجود حارس الإدخال المحدد وبصمة جسمه وإعداداته، ويرفض أي محفز إضافي غير مؤهل. جرى تحديث اختبار التزامن لاستدعاء المساعد نفسه داخل معاملة إزالة العميل الوهمي؛ لم يعد يكتفي بإزالة ارتباط يدوياً. فحص PostgreSQL المضمّن نجح بعد التعديل. يبقى تشغيل الجلستين في PostgreSQL17 شرطاً لم يُسجل نجاحه بعد. هذه الفقرة تحل محل تصميم القفل الحصري السابق، دون تفعيل الحذف الكامل.
