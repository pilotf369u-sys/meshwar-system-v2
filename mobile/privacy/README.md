# Isolated privacy implementation — not deployed

Branch: `app/privacy-controls-20261025`; rollback branch: `rollback/before-privacy-controls-20261025`. Review target is the preparation branch (PR #1106), not main. Do not merge the stacked app history wholesale into main.

## Behavior

- A signed-in customer explicitly requests deletion, reads only their own request status and may cancel. This does not erase, disable or log out the account, or alter orders/payments.
- Existing verified admin sessions access a paged queue. Admin can record verification, hold a request and inspect relation counts. No account-delete button or automatic account erasure is provided. Reviewed per-message text erasure is described separately below.
- Before review submission/photos, an unchecked content-policy agreement is required and saved with a version. The new submit wrapper calls the existing delivered-order validation. Insert guards also protect older submit/image endpoints; deploy the new frontend with the additive SQL as one reviewed change, not the SQL alone.
- Customers can report content or its author, block their reviews and undo a block. A report never hides a review automatically. Admin sees reported content and can dismiss or hide it; orders and prices are not changed. Blocking affects authenticated review details, not global rating summaries.
- New tables have RLS and no direct anon/authenticated grants. All public RPCs validate the existing custom server session. No customer ID is accepted as proof of ownership, and session tokens remain in POST bodies.

## Deliberately unfinished production erasure

`kinto_deletion_execute_v1` is disabled: no approved policy row is installed. It only handles a verified fresh profile in a reviewed schema. Associated rows, unknown logical customer relations, legacy local_orders or schema drift hold erasure. Existing production accounts with transactions are **not covered**. Real JSON identity snapshots, messages, Storage, backups and retention rules require a separate complete inventory and operational approval. Do not describe receiving a deletion request as completed account deletion or mark Play readiness true.

The executor briefly locks customer_review_sessions exclusively (500 ms lock wait) to finish in-flight validation transactions. This operational cost is another reason it must remain disabled until reviewed. A schema signature is only a drift gate, not proof of a complete identity inventory.

## Review media erasure (source only, disabled by default)

`sql/kinto-privacy-media-v1.sql` adds a private queue, separate empty/disabled policy plus the base enabled/reviewed erasure policy, bounded leases, and exact owner/path checks. Its RPCs are granted only to service_role and additionally validate the existing admin session and a verified customer request. Browser roles cannot prepare, claim paths or acknowledge completion. Only the server worker may remove an exact product-review-images key. It never deletes a Storage row with SQL, empties a bucket, follows client-supplied URLs, or touches order/payment/stock records. Legacy database image bytes are removed through the observed image-payload FK cascade. Source paths are cleared from completed jobs.

The new guards freeze leased source image identity/deletion and review owner/deletion, and prevent cancellation after an irreversible media phase starts. They only affect an explicitly approved active erasure lease, never normal reviews when the module remains disabled. Job-row locks coordinate source changes with claims; bounded waits/deadlocks fail closed. Interrupted operations retry with a new lease; three attempts then hold for review. Deleted files cannot be recovered by rolling back this SQL.

Server source: `supabase/functions/kinto-privacy-media-v1/`. Runtime switch KINTO_PRIVACY_MEDIA_ENABLED must also be explicitly true, and server env supplies its existing service key; no key is stored here or sent to clients. Each invocation processes at most one item, requires explicit matching request confirmation, and returns account_deleted=false even when media removal succeeds. On remove/list/access failure the source image remains and the queue retries. Verification lists the exact directory/name through authenticated Storage with a bounded search; a generic404 is not accepted as proof. SDK contract references: https://supabase.com/docs/guides/storage/management/delete-objects and https://supabase.com/docs/guides/storage/debugging/error-codes .

The module covers attached review images only, not uncommitted upload-ticket files, support-chat attachments, shared notices, account erasure, transaction retention or backups. No actual Storage calls, Edge deployment or production enablement have been performed. Mock Storage tests do not establish real SDK/provider behavior. Enablement remains prohibited until the complete deletion scope and actual storage permissions/settings are reviewed and coordinated.

Rollback: stop/drain worker first, execute `kinto-privacy-media-rollback-v1.sql`, then base privacy rollback/frontend restoration. Retain queues for reconciliation. Added RPC rights/guards are removed and policy disabled; rollback cannot recreate already removed data.

The competing-transaction test holds a real PostgreSQL claim open, attempts a concurrent source mutation with a200ms lock timeout, then verifies the committed lease still blocks identity changes and another worker sees no claimable item. It cleans its synthetic image/jobs/policy and restores the request status; no Storage API is involved. Base erasure disablement also shuts the media check gate, preventing an independently enabled media policy from bypassing base rollback.

## Account preferences and restore ledger (source only)

The existing gated fresh-profile finalizer now explicitly removes exact-owner cart data, favorite lists/items, notification-read state and block links to that erased account. It validates the observed UUID/composite ownership keys, rejects unreviewed incoming foreign keys or DELETE triggers, locks every managed table before deleting any row, and shares one transaction with token and profile removal. Unknown dependencies, financial accounts, chats, images and legacy mappings continue to hold the whole finalizer; preferences are not partially deleted on a held request. No new public endpoint or financial writes are added. Completed request verification notes and customer links are cleared.

A private ledger records a SHA256 digest of the random customer UUID, a receipt ID, sequence and completion time in the same transaction. It contains no raw customer UUID, name, contact details or tokens. These hashes are pseudonymous deletion evidence, not public anonymous data. The paged operator-only export must be preserved **outside the database** under access control: restoring an older database also restores an older, incomplete in-database ledger. Do not place real ledger exports in Git, the public website or app assets.

The private read-only restore matcher accepts externally preserved hashes, identifies reappearing customer hashes and always returns coverage_verified=false and restore_authorized=false. It is a detection aid, never automatic deletion or permission to expose a restored database. The actual provider/manual-backup expiry, externally durable checkpoint handling and safe reapplication of the complete erasure plan remain unverified. ## Reviewed text-only chat erasure (source only, disabled)

`kinto-privacy-chat-v1.sql` adds a private per-message review decision. Existing custom admin sessions can list20 messages of a verified request at a time, inspect bounded detail, approve one unchanged text or retain a specific message with a reason and a future review date. A review date is not automatic expiry. File-bearing or oversized messages cannot be approved for this eraser. No keyword guessing determines whether text is financial evidence: the administrator must review that decision. The existing admin privacy card opens a dialog; there is no new app/login page.

Actual text erasure is granted only to service_role, revalidates admin/request, requires exact message confirmation, an approved content hash, known table shape and no incoming FK, inheritance/rewrite rule or DELETE-trigger side effects. Ordinary read flags do not invalidate content approval. A compatible row-exclusive relation lock blocks conflicting DDL and approval is rechecked; the selected row is locked and exactly one deletion must occur. Failure to record completion rolls back the deletion. Other conversations/orders are not modified. Retained text and every attachment remain untouched by this operation. No whole-conversation delete or file erase is added.

The shared server handler accepts only the fixed erase_chat_text operation and exact signed-bigint identifiers. KINTO_PRIVACY_CHAT_ENABLED is separate and absent/false by default; the existing reviewed base SQL policy is also required. Service keys stay in server environment. Browser calls include custom admin tokens only in POST bodies; they cannot call the privileged SQL eraser with the public key. Browser preflight is limited to the two KINTO site origins; origin checks are not a substitute for the SQL session checks. The new function-only verify_jwt=false source stanza supports custom KINTO sessions; no existing function stanza changes or live service configuration/deployment occurs. Official auth/config reference: https://supabase.com/docs/guides/functions/auth-headers . This is not a live Edge/gateway qualification.

The private minimal chat ledger export retains only request/date and a hash of customer/message identity; it detects an older different text version after a simulated restore without storing the erased text. It needs an external coherent checkpoint like the account/media ledgers. Matching is read-only, never authorizes restore and does not claim full coverage. Cancellation after irreversible text erasure is blocked. Stop/drain the worker before running chat rollback, then media/base rollback; preserve decisions/evidence.

## Coherent external checkpoint source — private, offline, not deployed

`kinto-privacy-checkpoint-v1.sql` is a DB-owner-only STABLE read-only exporter. It collects completed account, review-media and chat-text identity hashes/dates from one calling-statement snapshot, including exact per-ledger counts. No request/customer/message IDs, raw paths, text or contacts leave the ledgers. Limits are explicit and overflow rejects the whole export instead of returning a partial checkpoint. The envelope binds the exact UTF8 payload bytes with SHA256. It never certifies recency, copy inventory, complete deletion coverage or restore authorization.

`checkpoint.py` runs offline: exact schema/ledger/count/hash/date/source checks, trusted expected digest required, bounded input, duplicate JSON-key rejection and exclusive new-file creation with mode0600 on supporting systems. The expected digest must be preserved in a separate trusted operator record: an adjacent checksum is not authentication or freshness proof. An old valid checkpoint still misses newer deletions. No output is produced on validation failure, and no existing destination/symlink is overwritten. Actual synced copies/permissions and external checkpoint lifecycle are not verified. See `mobile/release/ERASURE-CHECKPOINT-AR.md`; do not run against production before coordinated approval.
