# تجهيز تثبيت تغيير كلمة مرور العميل — PR #1118

الحالة: **جاهز للمراجعة والتجربة المعزولة، وليس إذناً لتنفيذ الإنتاج**. يبقى PR في Draft. لا دمج إلى main، ولا تحديث Hostinger، ولا تنفيذ SQL على Supabase الإنتاجية ضمن هذه المهمة.

## أساس المراجعة

نسخة الفرع عند بدء التجهيز: `7fb9320d622b780d6a724b787e597bd28df25da2`. أفاد المستخدم بأن الاعتماديات والتشفير ودالة الجلسة موجودة، ومالك دالة الجلسة وجدول customers هو postgres، وRLS مفعلة، ولا يملك anon أو authenticated أو PUBLIC صلاحية CREATE على المخططات المعنية. أفاد أيضاً بنجاح فحوص GitHub الأربعة عشر. هذه نتائج مقدمة من المستخدم وليست فحصاً جديداً منا لقاعدة الإنتاج.

المراجعة المحلية تؤكد أن RPC تستخرج هوية العميل من رمز الجلسة عبر الدالة الحالية؛ لا تقبل customer_id من المتصفح. كلمة المرور الحالية مطلوبة، ومقارنة bcrypt تدعم الحسابات المجزأة، والنجاح يرقّي كلمة المرور القديمة النصية إلى bcrypt. كلمة المرور الجديدة مقيدة بـ8–72 بايت. لا يُعاد أو يُسجّل رمز الجلسة أو كلمة المرور. قفل صف العميل يسلسل التغييرات بين جلساته، مع قفل مؤقت بعد خمس محاولات خاطئة. `SECURITY DEFINER` تستخدم `search_path=pg_catalog, pg_temp` والمراجع التطبيقية مؤهلة بالمخططات. دالة الجلسة الحالية تستخدم اعتمادياتها الحالية دون تعديل؛ منع CREATE في مخططاتها شرط ثقة يجب أن يبقى صحيحاً.

لا تتغير مدة الجلسة أو صلاحيتها ولا يتم تسجيل خروج العميل عند تغيير كلمة المرور. هذه سياسة الميزة الحالية، وليست آلية إبطال جميع الجلسات. لا تشكل المحاكاة أو PGlite بديلاً عن اختبار Supabase حقيقي منفصل قبل أي إنتاج.

## ترتيب تثبيت مستقبلي بعد موافقة منفصلة

1. ابدأ بمشروع Supabase تجريبي منفصل ببيانات وهمية فقط. راجع ملفات SQL وchecksum من نفس commit، واحتفظ بنتيجة فحص الاعتماديات وACL الحالية. لا تنسخ قاعدة العملاء أو أسرار الإنتاج.
2. راجع تقرير `review-existing-boundaries.sql` في البيئة التجريبية، ثم احصل على الدليل المكافئ من مسؤول البيئة المستهدفة قبل أي إنتاج. ملكية postgres ووجود RLS لا تثبتان وحدهما منع تزوير سجلات الجلسة أو تعديل كلمة المرور مباشرة. صلاحيات كتابة الجلسات أو قراءة/تعديل حقل password تتطلب مراجعة سياسات RLS الفعلية وصلاحيات الأعمدة؛ لا يكفي الحكم على GRANT وحدها. يجب إثبات عدم قدرة أدوار API على إنشاء جلسة بهوية عميل آخر أو تجاوز فحص الكلمة الحالية. إذا لم يثبت ذلك، يتوقف الإطلاق، ولا تصلح هذه الحزمة صلاحيات النظام الحالي. بيانات فحص المستخدم أعلاه لا تحسم هذه النقطة.
3. تحقق من غياب الكائنين: `private.customer_password_change_attempts_v1` و`public.customer_change_password_session_v1` بجميع overloads. وجود أي منهما يوقف التثبيت؛ لا تُعدّل المثبّت ليحل محله ولا تحذف الكائن السابق.
4. نفّذ **ملف install.sql كاملاً كمعاملة واحدة بحساب postgres** وبأداة تتوقف عند أول خطأ. لا تنفذ أجزاء منفصلة ولا تستخدم حساب API أو service_role. عند فشل التنفيذ تأكد من ROLLBACK قبل متابعة أي اتصال في SQL editor. هناك مهلة قفل 5 ثوانٍ وعبارة 30 ثانية؛ الفشل لا يبرر تجاوزها دون مراجعة.
5. شغّل `verify.sql` كاملاً للقراءة فقط بنفس السياق الإداري. يجب أن يرجع `PASSWORD_V1_VERIFY_OK` ولا أي استثناء. يجب ألا يعرض صفوف عملاء أو كلمات مرور أو رموز.
6. تحقق من تعرف PostgREST على RPC في البيئة التجريبية عبر API. قد تتطلب رؤية الدالة تحديث cache المخطط بالطريقة المدعومة في المشروع. لا يحتوي المثبّت على NOTIFY ولا يغير إعدادات PostgREST؛ تحديث cache خطوة تشغيلية منفصلة بعد الموافقة. ظهور PGRST202 يعني مشكلة cache/رؤية، ولا يعني نجاح الاختبار.
7. نفّذ خطة الحسابات الوهمية أدناه. لا تنشر واجهة الإنتاج قبل توفر RPC وفحص الصلاحيات والاختبار الحقيقي المنفصل. نشر الواجهة أو SQL الإنتاج يحتاج قراراً جديداً؛ الملفات لا تنفذ النشر تلقائياً.

## اختبار الصلاحيات بعد التثبيت

يجب أن ينجح `verify.sql` ويثبت: مالك RPC والجدول postgres؛ الدالة SECURITY DEFINER وsearch_path المقيد وبصمة جسمها مطابقة؛ لا منح PUBLIC أو منح غير متوقعة على RPC؛ EXECUTE لـanon وauthenticated دون grant option؛ لا منح على جدول المحاولات لغير المالك ولا سياسات RLS غير متوقعة؛ RLS مفعلة؛ الصلاحيات الفعلية لأدوار API لا تسمح بقراءة/إدراج/تعديل/حذف/اقتطاع جدول المحاولات؛ USAGE على public موجودة مسبقاً، ولا CREATE على مخططات الاعتماديات.

في المشروع التجريبي فقط، تحقق عبر عميل API الفعلي لكل من anon وauthenticated: استدعاء RPC برمز جلسة غير صالح يرجع استثناء الجلسة ولا يغيّر أي كلمة مرور. لا تفترض أن وجود Supabase Auth JWT وحده يحدد العميل؛ التفويض الفعلي هنا برمز جلسة العميل الحالي. استخدم قيماً وهمية، واحتفظ بنتيجة نجاح/رفض ورمز الخطأ فقط. لا تحفظ bodies أو Authorization أو session token أو كلمات المرور في الأدلة.

جرّب الوصول لجدول المحاولات عبر أدوار API: يجب رفضه. عدم نشر private في PostgREST وحده لا يكفي؛ تحقق SQL من امتيازات الجدول الفعلية مستقل عن إعداد cache أو exposed schemas. الفحص الحالي لا يغير إعدادات exposed schemas.

## خطة حساب وهمي مخصص

- حضّر حسابين A وB ببيانات وهمية فريدة في المشروع التجريبي المنفصل، مثلاً معرفات مرتبطة بـ`pr1118-qa` وبريد من نطاق `example.invalid` إن كان مسار التسجيل الحالي يدعمه. لا تستخدم رقم شخص حقيقي أو ترسل SMS/WhatsApp حقيقية. تهيئة الحسابات تتم بالوسيلة المدعومة في بيئة الاختبار، دون تعديل كود التسجيل/الدخول أو seed SQL للإنتاج. لا توجد أوامر إنشاء عملاء إنتاجية في الحزمة.
- احفظ كلمات مرور التجربة خارج التقرير والسجلات، وادخل عبر نظام الدخول الحالي دون تغييره. افتح شاشة كلمة المرور على نسخة الواجهة المتصلة حصراً بالمشروع التجريبي. راجع عنوان مشروع Supabase قبل البدء، ولا تستخدم session token من الإنتاج.
- النجاح: غيّر كلمة A بالكلمة الحالية الصحيحة. يجب ظهور النجاح، وقبول الجديدة ورفض القديمة في اختبار الدخول القائم. تحقق أن اسم A وعنوانه وبقية حقوله لم تتغير وأن B ما زال يدخل بكلمته الأصلية. لا تفحص القيم الفعلية لكلمات المرور أو تعرضها في الأدلة؛ يكفي أن التخزين مجزأ وأن الحقول الأخرى ثابتة.
- الفشل: كلمة حالية خاطئة، تأكيد غير مطابق، جديدة قصيرة أو أكبر من 72 بايت أو مطابقة للحالية. لا يتغير الحساب. بعد خمس محاولات خاطئة تُرفض محاولة صحيحة مؤقتاً؛ انتظر 15 دقيقة في التجربة الحقيقية، ولا تعدّل ساعة/جدول الإنتاج لتجاوز القفل. تأكد أن B غير مقفول بسبب محاولات A.
- عزل الحسابات: استخدم جلسة B وكلمة A؛ يجب رفض التغيير وبقاء الحسابين سليمين. جرّب جلسة A أخرى للتأكد أن قفل المحاولات مشترك بين جلسات الحساب نفسه.
- الجلسة: اختبر الرمز الغائب وغير الصالح. انتهاء الجلسة/إلغاؤها يحاكى في fixtures المعزولة فقط، أو ينتظر انتهاء جلسة فعلية في المشروع التجريبي دون تغيير كود الجلسات. شكل الاستثناء الحالي `P0001` و`message=REVIEW_SESSION_INVALID` أو `REVIEW_SESSION_REQUIRED`؛ الواجهة تعرض «انتهت جلسة الدخول. يرجى تسجيل الدخول مرة أخرى» ولا تسجل خروجاً تلقائياً. لا تطبع الرموز.
- عطل الشبكة: رسالة تعذر الخدمة دون كشف تفاصيل حساسة، مع إعادة تمكين زر الحفظ. وثّق النتائج المختصرة لكل حالة، لا تسجيل HAR أو request bodies تحتوي أسراراً.

## التراجع الآمن

إذا لم تُنفّذ معاملة التثبيت بنجاح، يكفي ROLLBACK للمعاملة الفاشلة؛ لا تشغّل rollback.sql على كائن سابق مجهول. إذا تم التثبيت، يتطلب التراجع موافقة تشغيلية منفصلة وتنفيذ `rollback.sql` كاملاً. الحارس يرفض التشغيل إن تغير المالك أو علامة الحزمة أو بصمة جسم RPC؛ لا تتجاوز الحارس تلقائياً.

التراجع يحذف **الدالة الجديدة فقط** ويستخدم RESTRICT؛ وجود كائنات تعتمد عليها يوقفه دون CASCADE. جدول المحاولات والقفل يبقى كما هو، ولا تُحذف/تُعدّل صفوف العملاء أو الجلسات. كلمات المرور التي غُيرت بنجاح قبل التراجع تبقى مجزأة وبالقيم الجديدة؛ لا يمكن ولا يجب استعادة كلمات المرور القديمة. الطلب الجاري الذي بدأ قبل التراجع قد يكتمل؛ التراجع ليس إلغاءً بأثر رجعي. تحقق بعده من غياب توقيع RPC ومن بقاء جدول القفل محمياً، ونسّق إخفاء مدخل الميزة/إبطال cache لاحقاً ضمن مسار نشر مستقل مصرح به. لا تغيّر تسجيل الدخول أو صلاحياته.

بعد التراجع، يرفض المثبّت إعادة التشغيل لأن جدول المحاولات محفوظ. إعادة التفعيل تحتاج حزمة منفصلة مدروسة تعيد استخدام الحالة بأمان؛ لا تحذف الجدول ولا تستخدم CREATE OR REPLACE لتجاوز ذلك. إعادة تنفيذ rollback.sql ترفض أيضاً بدلاً من لمس كائنات غير معروفة.
