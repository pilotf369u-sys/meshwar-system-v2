# KINTO — المواصفات الفنية لربط شركات الدفع الإلكتروني

**تاريخ الوثيقة:** يُكتب عند إرسالها إلى شركة الدفع، ولا يُثبت بتاريخ إعداد المسودة.  
**المرجع:** [GitHub Issue #989](https://github.com/pilotf369u-sys/meshwar-system-v2/issues/989) وقرارات المشروع المعتمدة.  
**الحالة:** وثيقة تكامل فني قابلة للتحديث حسب متطلبات الشركة، وليست إثباتاً بأن ربط الشركة قد نُشر.

## 1. التعريف بالنشاط التجاري

**KINTO منصة يديرها تاجر واحد يملك عدة متاجر أو أسماء وعلامات تجارية تابعة له**، وقد تظهر للعميل بأسماء مختلفة. ليست هذه المتاجر تجاراً مستقلين من أطراف ثالثة يستلزم كل منهم حساب تسوية منفصلاً.

يُطلب ربط وسائل الدفع ضمن علاقة تعاقدية واحدة مع التاجر، وتُحوّل حصيلة المدفوعات إلى **الحساب المصرفي المحدد باسم التاجر** وفق شروط شركة الدفع. تعدد أسماء المتاجر أو فواتيرها داخل KINTO لا يعني تعدد المستفيدين من التسوية.

لا تتناول هذه الوثيقة مصدر المنتجات أو طريقة شراء التاجر لها أو توريدها، فهي مسائل تشغيلية منفصلة عن آلية تكامل بوابة الدفع.

## 2. الهدف الفني

تملك KINTO منظومة موحدة للسلة ومراجعة الطلب والتسعير والحجز وتسجيل المدفوعات واعتماد الطلبات والتفرعات والفواتير. يُربط كل مزود جديد عبر **Gateway Adapter** مستقل، بحيث لا تتغير منظومة الشراء الأساسية عند الانتقال من محاكي الاختبار الحالي إلى شركة الدفع المتعاقد معها.

**لا يعاد تصميم** السلة أو الفواتير أو مخزون المنتجات والتفرعات أو الخصومات والقسائم أو الحملات والهدايا أو دورة الموظف والتاجر والأدمن.

## 3. رحلة الطلب والدفع

1. يختار العميل منتجات من متجر أو عدة أسماء متاجر مملوكة للتاجر نفسه. وتبقى طلبات العروض المباشرة عبر مسارها المنفصل.
2. يراجع العميل المنتجات والصور والخيارات والكميات والأسعار والخصومات والقسائم المؤهلة. الشحن غير مشمول في مبلغ المنتجات ويُحدد لاحقاً بحسب سياسة KINTO.
3. يعيد الخادم التحقق من هوية العميل والأسعار والصرف والاستحقاقات والمخزون، ويحجز الكميات المؤهلة مؤقتاً مع منع التكرار.
4. تنشأ عملية دفع واحدة بالمرجع **KP** لكل شراء، حتى إذا شملت السلة أكثر من اسم متجر تابع للتاجر.
5. يبدأ موصل الشركة جلسة الدفع وفق وسيلة الربط التي تدعمها. لا يُعتد برسالة نجاح المتصفح وحدها؛ يعتمد الخادم نتيجة موثوقة من الشركة عبر الإشعار الموقّع أو الاستعلام الرسمي.
6. بعد التأكيد الموثوق، يُعتمد الطلب مرة واحدة: **KN مستقل وفاتورته الأصلية لكل متجر**، مع خصم المخزون والتفرعات مرة واحدة والانتقال إلى **«تم التسديد»**.
7. تستمر عمليات الموظف والتاجر والأدمن والشحن والتتبع والباركود والمكافآت كما هي، ويعرض تبويب «مدفوعاتي» KP وأرقام KN والفواتير المرتبطة به.
8. تعالج حالات الرفض والإلغاء والانقطاع والتأكيد المتأخر والإشعارات المكررة دون تكرار تحصيل أو طلب أو خصم مخزون.

## 4. طرق الربط التي قد توفرها شركة الدفع

| الطريقة | ما يلزم من الشركة | قاعدة التحقق |
|---|---|---|
| **Hosted Checkout / Redirect** | إنشاء جلسة وصفحة دفع مستضافة وروابط عودة | العودة إلى الموقع لا تكفي لتأكيد الدفع |
| **Embedded / SDK** | واجهة آمنة وحقول مستضافة أو رمز دفع | لا تستقبل KINTO بيانات البطاقة المصرفية الخام |
| **Server API + Webhook** | API خادمي وإشعارات وتوقيع موثق | يتحقق الخادم من التوقيع والحالة والمبلغ والعملة |
| **Payment Link** | رابط دفع مرتبط بمرجع KP | تطابق النتيجة خادمياً قبل الاعتماد |
| **QR** | رمز صادر عن الشركة ومربوط بالعملية | مسح الرمز وحده لا يثبت الدفع |

قد تدعم الشركة طريقة واحدة أو عدة طرق. **يُختار موصلها حسب وثائقها الفعلية، وليس بفرض طريقة ربط مسبقة.**

## 5. عقد Gateway Adapter

لكل مزود موصل خادمي منفصل مسؤول عن:
- وصف الإمكانيات والعملات ووحدات المبالغ ومهلة العملية.
- إنشاء جلسة الدفع بمعرف المحاولة وKP والمبلغ والعملة المحسوبة خادمياً، ومفتاح منع التكرار.
- عرض تعليمات الدفع الآمنة دون تسليم أسرار الشركة للمتصفح.
- التحقق من التوقيع والمرجع والحالة والعملة والمبلغ وحساب التاجر وسياق العملية.
- الاستعلام عن حالة العملية المعلقة وإعادة المطابقة عند انقطاع الاتصال.
- دعم الإلغاء والاسترداد أو الاسترداد الجزئي بحسب إمكانات الشركة، مع سجلات تدقيق ومنع تكرار التنفيذ.

**الموصل لا ينشئ الطلبات ولا يخصم المخزون ولا يغير «تم التسديد» بنفسه.** بعد نتيجة دفع خادمية موثقة، يستدعي المحرك المشترك آلية الاعتماد القائمة.

## 6. التسوية التجارية والمتاجر التابعة

- جميع المتاجر والأسماء التجارية المعروضة في KINTO تابعة لنفس التاجر.
- يمكن أن تتضمن العملية الواحدة KP عدة طلبات KN وفواتير تفصيلية للأسماء التجارية التابعة، بينما تظل علاقة التحصيل والتسوية **مع التاجر نفسه**.
- نطلب من الشركة تأكيد إمكان إظهار اسم المتجر التابع أو KN في وصف العملية أو تفاصيلها **مع بقاء حساب التسوية واحداً**.
- نطلب بيان الرسوم، وعملة التحصيل والتسوية، وآلية تحويل المستحقات إلى الحساب المصرفي المحدد.
- لا ينبغي استنتاج أن KINTO لا تستقبل مستحقات مالية؛ فالمقصود هنا تحديد **طريقة تحصيل المدفوعات وتحويلها للتاجر** عند تفعيل الشركة الحقيقية.

## 7. معلومات نطلبها من شركة الدفع

1. متطلبات اعتماد تاجر فرد يمتلك عدة علامات ومتاجر تابعة له، وشروط الحساب المصرفي المستفيد.
2. طرق الربط المتوفرة ووثائق API/SDK والإصدارات المدعومة.
3. العملات المتاحة، خصوصاً الدينار العراقي، والحدود والرسوم وأوقات التسوية.
4. إنشاء جلسات الدفع، ومعرف العملية، والمهلة، وإعادة المحاولة، وإلغاء العمليات.
5. آلية التوقيع والتحقق من Webhook، وإعادة الإرسال، والاستعلام عن الحالة.
6. الاسترداد الكامل والجزئي والمطابقة المالية والاعتراضات على العمليات.
7. متطلبات النطاق HTTPS وCallback وWebhook وقيود التطبيقات والهواتف.
8. بيانات الاختبار Sandbox وإجراءات الانتقال إلى التشغيل التجاري.
9. هل تتولى الشركة الربط الفني أم توفر واجهات وأدلة لينفذها فريق KINTO؟

## 8. ما نقدمه للشركة بعد تحديد طريقة الربط

- رابط موقع KINTO ونطاق HTTPS المعتمد **عند استكمال الاعتماد**.
- بيانات التاجر التجارية المطلوبة وبيانات الاتصال الفني.
- أمثلة غير حساسة لمرجع KP وKN والمبلغ والعملة وآلية توزيع فواتير المتاجر التابعة.
- روابط Return / Callback / Webhook **بعد تنفيذها والتحقق منها**، لا تُخترع مسبقاً.
- حالات الاختبار: نجاح ورفض وإلغاء وتأخر وانقطاع وتكرار حدث، وسلة تضم عدة أسماء متاجر تابعة، واسترداد بحسب ما تدعمه الشركة.

لا نرسل مفاتيح Supabase الخاصة أو `service_role` أو كلمات المرور أو جلسات العملاء أو بيانات العملاء الكاملة أو أسرار الخادم. تحفظ بيانات توثيق بوابة الدفع السرية في الخادم فقط.

## 9. المحاكي الحالي والانتقال لشركة حقيقية

محاكي KINTO هو **مزود تقني مؤقت للاختبارات أثناء التطوير** يستخدم مسار الطلب والدفع نفسه. لا تعني نتيجة المحاكاة وجود تحويل مصرفي، ولا تعد هذه الآلية وصفاً لنموذج التحصيل التجاري المستقبلي.

عند اختيار شركة دفع فعلية، تُنفذ فقط متطلبات موصلها والتحقق من التوقيع والتسوية والاختبارات الخاصة بها؛ ولا يعاد بناء السلة أو مراحل KN والفواتير والطلبات.

## 10. شروط الاعتماد والنشر

- اختبار الربط الجديد وفق وثائق الشركة الحقيقية.
- التأكد من مطابقة المبلغ والعملة وKP ومرجع المزود ومنع التكرار.
- اختبار سلة متعددة الأسماء التجارية التابعة للتاجر: KP واحد وKN وفاتورة أصلية لكل متجر.
- فحص المخزون والتفرعات والعروض والقسائم والشحن والصلاحيات.
- اعتماد التشغيل من مالك KINTO بعد التحقق من الأمان والمطابقة.

## 11. أمور تُستكمل لاحقاً

شركة الدفع، عنوان الموقع النهائي، الاستضافة، روابط Callback/Webhook، بيانات الاعتماد، حساب التسوية المحدد، والتاريخ الفعلي لإرسال هذه المواصفات؛ جميعها تُثبت عند الاختيار والتعاقد، ولا تُفترض الآن.
